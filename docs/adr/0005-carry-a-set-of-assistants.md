# ADR 0005: Carry a Set of Assistants Rather Than One

Status: Accepted

## Context

The contract held one assistant. Switching created the new harness's pointer and left the
previous one in place, and Project Check required only the currently selected pointer, so a
project that had moved from Claude Code to Cursor kept a stale `CLAUDE.md` that nothing
reported and nothing owned.

Research teams mix harnesses on one repository. A student on Cursor, a collaborator on Claude
Code, and a lead on OpenCode share one project, and the single field cannot express that. In
practice the contract is edited by hand or the extra harness goes unsupported.

Removing a retired assistant from the enum is not available as a simplification. The contract
model forbids unknown values, so deleting a member makes any project recording it fail
validation and become unloadable. A tool upgrade must never strand existing work.

## Decision

The contract carries a non-empty, order-preserving, deduplicated list of assistants.
Generation renders one activator per selected assistant, and adding an assistant later creates
only its missing artifact.

A scalar value migrates to a single-element list on load, so every existing contract keeps
working without researcher action. No assistant is removed from the enum; a retired one is
retained and adapted, and continues to load.

Deselecting an assistant reports its artifacts and deletes nothing, matching how capability
deactivation already behaves. Launch stays a single deliberate choice, because starting a
session is one act even when a project serves several harnesses.

## Consequences

- One project can serve a mixed team without hand-editing the contract.
- The stale-pointer defect is resolved by reporting rather than deletion, consistent with never removing researcher files.
- The contract schema changes, so the wizard, settings, dashboard, check, launch, and goldens all move together in one reviewed change.
- A project selecting several harnesses carries several small activators, which is the cost of serving several harnesses.
- Retaining retired enum members means the list grows monotonically and carries entries the wizard no longer offers.
- Because migration is additive, a project generated by upstream continues to load unchanged.
