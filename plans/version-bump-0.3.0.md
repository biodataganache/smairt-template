# Plan: Version bump to 0.3.0 and clean local install

## Why bump

`scaffold_version` is the only thing that tells a project whether its guidance matches the
installed tool. [`project_check()`](../src/smairt/project.py:588) compares the string in
`smairt.yaml` to `__version__`, and
[`_require_current_scaffold()`](../src/smairt/project.py:841) blocks capability changes,
repair, and regeneration when they differ.

So a project generated before `4169b3b` and one generated after both claim `0.2.0`, while
the second has five additional assets and nine rewritten ones. The check cannot see the
difference, and reports a stale project as current.

## Why 0.3.0 rather than 0.2.1

The blueprint gained five declared assets and the workflow gained a vocabulary. A researcher
on `0.2.0` following `0.3.0` documentation would look for `analysis/ITERATION_LOG.md` and
three helpers that their project does not contain. That is a change in what a project *is*,
not a fix, so the minor version moves.

[ADR 0001](../docs/adr/0001-protect-generated-project-surface.md:21) ties a project to its
recorded scaffold version and defers migration to an explicit upgrade flow. The bump is what
makes that deferral honest: without it, the tool cannot tell which projects would need
upgrading.

## Every place the version appears

Found by searching for `0.2.0` across the repository. Two of these are load-bearing and
easy to miss.

| File | Occurrence | Notes |
|---|---|---|
| `pyproject.toml` | `version = "0.2.0"` | The package version |
| `src/smairt/__init__.py` | `__version__` | What `--version` prints and what the check compares |
| `src/smairt/models.py` | `scaffold_version` default | Written into every new `smairt.yaml` |
| `uv.lock` | `version = "0.2.0"` | Regenerated by `uv sync`, not edited |
| `tests/test_cli.py` | `"smairt 0.2.0"` and a contract assertion | Two separate places |
| `tests/fixtures/golden/*/smairt.yaml` | three files | Regenerated by `update_goldens.py` |
| `.github/workflows/ci.yml` | two artifact filenames | **Breaks CI if missed** |
| `.github/CONTRIBUTING.md` | two artifact filenames | Developer-facing commands |
| `README.md` | two artifact filenames | Developer-facing commands |
| `.github/ISSUE_TEMPLATE/bug_report.md` | example version | Cosmetic; leave or update |

The CI workflow is the risk. It runs
`smoke_install.py --artifact dist/smairt-0.2.0-py3-none-any.whl`, so after a bump `uv build`
produces `smairt-0.3.0-*` and CI fails on a missing file. The README and CONTRIBUTING carry
copies of the same two commands, so six filename references have to move together.

## Steps

1. Confirm the working tree is clean and matches `origin`
2. Update `pyproject.toml`, `__init__.py`, and `models.py`
3. Update the two assertions in `tests/test_cli.py`
4. Update the six artifact filenames in `ci.yml`, `CONTRIBUTING.md`, and `README.md`
5. Run `uv sync --all-extras` so `uv.lock` records `0.3.0`
6. Regenerate goldens, so the three `smairt.yaml` fixtures carry `0.3.0`
7. Run the full gate sequence, including a build and both smoke installs against the
   **`0.3.0`** artifacts
8. Record the bump in `docs/scaffold-transition.md`, including what a `0.2.0` project lacks
9. Commit and push
10. Reinstall locally with `uv tool install --force .` and confirm `smairt --version` reports
    `0.3.0`

## Verification that matters

- `smairt --version` prints `0.3.0`
- A freshly generated `smairt.yaml` records `scaffold_version: 0.3.0`
- `smairt check` on that project passes
- `smairt check` on a project generated at `4af22f8` reports the version mismatch rather
  than silently accepting it

The last one is the point of the exercise, so it should be checked explicitly rather than
assumed.

## Note on existing projects

A `0.2.0` project will now be told its scaffold differs, and capability changes, repair, and
regeneration will refuse until an upgrade flow exists. That is the designed behavior, and
preferable to the current state where the tool treats a stale project as current. Anyone
holding a `0.2.0` project who wants the new workflow should generate a new project rather
than expect a migration.
